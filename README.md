# RetireSafe

**Preventing takeover risks during cloud-resource retirement.**
Hacker Sprint, Manipal Bengaluru, research and solution-design phase.

When a cloud resource (an S3 bucket, an Azure app, a temporary event site) is deleted, the *trust placed in its address* often survives. DNS records, application configs, SPF rules, code and automated clients keep pointing at a name that someone else can re-register. RetireSafe is a proposed **retirement pre-flight**. Given a planned deletion, it collects evidence from every place that trust can hide and returns a per-condition verdict, *cleared*, *blocking* or *unknown*, together with a migration patch. It never returns an unqualified "safe".

This repository contains the **research, the proposed solution, and three test beds that were run on real public data**. The product itself has not been built yet; that is the hackathon's job. Every number in the dossier comes from a script and a committed output file in this repo.

## Headline results (real data, nothing fabricated)

| Test bed | Real data | Result |
|---|---|---|
| **TB1**: base rate of reclaimable references | 16,000 live hostnames from the Cisco Umbrella top-1M, the *can-i-take-over-xyz* fingerprints, and a live read-only S3 probe | **5 reclaimable candidates (0.031%, 95% CI 0.013–0.073%)**: 4 S3 `NoSuchBucket` and 1 Azure NXDOMAIN, plus 5 stale CNAMEs and 4 provider matches that need an HTTP check |
| **TB2**: "is this endpoint really dead?" | NASA-HTTP July 1995 log, **1,891,715 requests**, 7,133 resources | To be 99% sure a resource is dead you need **42 days of silence (median) and up to 127 days (tail)**. A naive Poisson model **over-predicts** returns by 1.48× (1,161 predicted vs 783 observed): it ranks resources well but is mis-calibrated as a probability |
| **TB3**: the coordination gap | Same NASA log | **108 of 108** resources that look idle on a 3-day dashboard had external clients in their history. `/shuttle/countdown/count.gif` had **0** recent hits and **15,054** distinct external clients |

Full method, numbers and caveats for each: [`docs/02_testbeds.md`](docs/02_testbeds.md).

## Reproduce everything

```bash
pip install -r requirements.txt
./scripts/fetch_data.sh                 # NASA logs, fingerprint catalogue, Umbrella top-1M → ./data

cd testbeds
python3 tb1_dns_cname.py                # live DNS + S3 API; ~7 min for 16k names (N_TOP / N_RAND env vars)
python3 tb2_traffic_survival.py         # ~1 min
python3 tb3_blast_radius.py             # ~1 min
python3 make_figs.py && python3 make_pdf.py   # regenerates figs/ and ../RetireSafe_Solution_Dossier.pdf
```

* TB1 needs outbound DNS and HTTPS to `s3.amazonaws.com`. It uses the system resolver.
* TB1 queries **live** infrastructure, so re-running it on a different day will give slightly different counts. The Umbrella list also changes daily; we used the 2026-10-01 copy.
* TB1 writes per-hostname results to `testbeds/results/tb1_raw.private.jsonl`, which is **git-ignored on purpose** (see [ethics](docs/06_ethics_and_limitations.md)). Only aggregates are committed.

## The problem in one diagram

```
CREATE ──► CONNECT ──► RETIRE ──────────► RECLAIM ──────────► INHERIT
app/bucket  event.example.com   resource deleted,   attacker registers    users/software trust
            → resource          DNS/code/SPF        the released name     attacker's content
                                reference survives
```

A takeover needs **all five** conditions: *resource released*, *name reassignable*, *reference survives*, *consumer remains*, and *controls permit impact*. RetireSafe evaluates each one with evidence and reports the ones it cannot evaluate as **unknown**. See [`docs/01_problem_and_evidence.md`](docs/01_problem_and_evidence.md).

## Proposed solution in one paragraph

**Collect** references from DNS exports, repositories, IaC plans and SPF records. **Probe** whether each name could be reclaimed and whether a provider protection already covers it. **Observe** runtime traffic using the TB2/TB3 engine, which gives per-resource quarantine windows, blast radius and the share of external clients. **Fuse** all of this into an evidence graph. **Decide** using a five-factor risk score in which unknowns widen the interval instead of being assumed away. **Act** by producing a blocked deletion with a precise reason, a migration patch, a "retain the name" recommendation, and an evidence record. Details: [`docs/03_architecture.md`](docs/03_architecture.md).

## Status and honesty boundaries

* ✅ Research, problem model, architecture and maths are written up.
* ✅ Three test beds were run on real data, with committed outputs.
* ⏳ The product (scanners, decision engine, CLI, demo) is the hackathon build. See [`docs/07_hackathon_plan.md`](docs/07_hackathon_plan.md).
